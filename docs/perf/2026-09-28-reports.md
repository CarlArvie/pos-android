# Performance & Scalability Optimization: Reports & Analytics

**Date:** 2026-09-28  
**Feature:** `reports` (Executive P&L, sales aggregation, top products/categories, payment breakdown, customer ranking, staff leaderboard, operating expenses, and inventory health)  
**Branch:** `perf/reports`  
**Target Hardware:** Low-end Android (2GB RAM, 720p/360-390dp width, Android 8-10)  
**Highest Evidence Tier Reached:** `[Verified]` (all 135 tests pass, 0 static analyzer issues in slice, deterministic query chunking verified up to 1,050+ transactions without SQLite variable limit errors, cached future state, O(I+P) linear valuation, and zero GPU raster blur passes)

## 1. Findings & Issues Addressed

1. **SQLite 999 Variable Parameter Limit (`[Verified]`)**:
   - **Issue:** Previously, `posDao.getSalesReportData()` queried `transactionItems` and `tenderPayments` using `isIn(txIds)` where `txIds` was an unconstrained list of all transactions in the selected period. If a period exceeded 999 transactions, Android SQLite threw an unhandled exception: `SqliteException(1): too many SQL variables`.
   - **Fix:** Implemented 500-element batch chunking across `txIds` with `Future.wait` parallel retrieval. Verified with characterization test inserting 1,050 transactions and aggregating across all lines and tenders with zero errors.

2. **Full-Table Memory Allocation Churn (`[Verified]`)**:
   - **Issue:** On every report calculation, `posDao.getSalesReportData()` performed 4 separate full-table loads: `select(products).get()`, `select(productTypes).get()`, `select(customers).get()`, and `select(employees).get()`. In a production store with 10,000 catalog items and 5,000 customers, this forced deserializing over 15,000 objects into memory, even if only 10 items were sold during the selected time period.
   - **Fix:** Replaced full-table scans with selective set-based dimension loading (`usedProductIds`, `usedCustomerIds`, `usedEmployeeIds`). Only referenced dimensions are loaded in safe 500-element chunks, cutting object allocations by > 90%.

3. **Uncached Future in `build()` (`[Verified]`)**:
   - **Issue:** `reports_view.dart` initialized `future: posDao.getSalesReportData(...)` directly in `FutureBuilder.build()`. Switching tabs between "Sales & Profit" and "Inventory Health" triggered redundant re-fetches and query churn.
   - **Fix:** Cached `_salesReportFuture` in state, initialized in `initState()`, and only refreshed when date preset, custom date range, or `_refreshKey` changes.

4. **$O(I \times P)$ Quadratic Valuation Calculation in `build()` (`[Verified]`)**:
   - **Issue:** In `reports_view.dart`, lines 133-139 ran a nested loop searching `products.where((p) => p.id == inv.productId)` for every inventory record on the main thread on every frame, even on the Sales tab.
   - **Fix:** Switched to an $O(1)$ product price map `prodPriceMap = {for (final p in products) p.id: p.price}`, reducing valuation computation to $O(I + P)$ linear time, and gated the computation so it only runs when on the "Inventory Health" tab (`_activeTab == 1`).

5. **Continuous Drift Query Stream Re-creation (`[Verified]`)**:
   - **Issue:** `StreamBuilder` called `(widget.db.select(...)).watch()` inside `build()`, creating new stream instances on every rebuild pass.
   - **Fix:** Initialized persistent `_productsStream` and `_inventoriesStream` in `initState()` with clean `didUpdateWidget` handling.

6. **GPU Raster Pass Overhead (Blurred `BoxShadow`) (`[Verified]`)**:
   - **Issue:** `_buildPnlCard`, `_buildMiniStat`, `_buildInventoryHealthCard`, and `_StatCard` utilized multi-pixel blurred `BoxShadow`, forcing expensive off-screen raster passes on low-end Mali/Adreno GPUs.
   - **Fix:** Replaced with crisp flat `Border.all(color: AppTheme.cardBorderColor)`.
